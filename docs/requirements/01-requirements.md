## 1. 개요

### 1.1 목적
본사와 여러 매장으로 운영되는 소규모 유통 사업자의 **상품 · 판매 · 재고 · 발주/입고** 업무를 하나의 Web 시스템에서 통합 관리한다.
판매와 입고가 발생하면 재고와 재고 이력이 함께 변경되도록 하여, 업무 데이터와 재고 데이터가 항상 일치하도록 한다.

### 1.2 운영 전제
- 본사 1곳과 여러 매장으로 운영한다.
- 상품 · 카테고리 · 공급처는 **본사가 관리하는 전 매장 공통 정보**다.
- 재고 · 판매 · 발주는 **매장별로** 관리한다.
- 판매가는 전 매장 동일하며, 부가세 포함 금액이다.

### 1.3 시스템 범위

| 업무 | 주요 기능 |
|---|---|
| 인증 | 로그인, 로그아웃, 내 정보 조회 |
| 매장 관리 | 매장 등록 · 수정 · 조회 · 사용 중지 |
| 사용자 관리 | 계정 등록 · 수정 · 조회 · 비활성화 |
| 기준정보 | 카테고리, 상품, 공급처 관리 |
| 판매 | 판매 등록, 조회, 취소 |
| 재고 | 재고 조회, 재고 이력, 재고 조정, 안전재고 설정, 부족 재고 조회 |
| 발주 | 발주 등록 · 수정 · 승인 · 입고 · 취소, 발주 조회 |
| Dashboard | 매출 현황, 재고 부족 현황, 최근 판매 · 발주 |

범위에서 제외한 기능은 [9. 범위 제외](#9-범위-제외-2차-검토-대상) 참고.

## 2. 사용자 역할

| 역할 | 대상 | 소속 매장 | 데이터 범위 |
|---|---|---|---|
| ADMIN | 본사 관리자 | 없음 | 전 매장 |
| MANAGER | 매장 관리자 | 1개 매장 | 소속 매장 |
| USER | 매장 직원 | 1개 매장 | 소속 매장 |

- 권한은 **역할(무엇을 할 수 있는가)** 과 **데이터 범위(어느 매장 데이터인가)** 두 가지 기준으로 판단한다.
- 회원가입은 없으며, 모든 계정은 ADMIN이 생성한다.

## 3. 업무 구분 코드

요구사항 ID는 `REQ-{업무코드}-{번호}` 형식을 사용한다. 이후 화면 목록 · API 명세에서 이 ID로 추적한다.

| 업무코드 | 업무 |
|---|---|
| AUTH | 인증 |
| STORE | 매장 관리 |
| USER | 사용자 관리 |
| CAT | 카테고리 |
| PROD | 상품 |
| SUPP | 공급처 |
| SALE | 판매 |
| STOCK | 재고 |
| PO | 발주 |
| DASH | Dashboard |

## 4. 기능 요구사항

**사용 역할 표기**: `A` = ADMIN, `M` = MANAGER, `U` = USER
**우선순위**: `필수` = 1차 개발 범위, `선택` = 일정에 따라 포함

### 4.1 인증 (AUTH)

|---|---|---|---|---|
| REQ-AUTH-001 | 로그인 | 아이디 · 비밀번호로 로그인하고, 성공 시 인증 토큰(JWT)을 발급한다. 비활성 계정은 로그인할 수 없다. | A, M, U | 필수 |
| REQ-AUTH-002 | 로그아웃 | 클라이언트에 보관한 인증 토큰을 삭제한다. | A, M, U | 필수 |
| REQ-AUTH-003 | 내 정보 조회 | 로그인한 사용자의 이름, 역할, 소속 매장을 조회한다. | A, M, U | 필수 |
| REQ-AUTH-004 | 비밀번호 변경 | 현재 비밀번호를 확인한 뒤 본인 비밀번호를 변경한다. | A, M, U | 선택 |

| ID | 규칙 |
|---|---|
| BR-001 | 모든 금액은 원 단위 정수이며 부가세 포함 금액이다. |
| BR-002 | MANAGER · USER는 소속 매장의 데이터만 조회 · 처리할 수 있다. 다른 매장 데이터 요청은 거부한다. ADMIN은 전 매장 데이터를 다룬다. |
| BR-003 | 권한과 데이터 범위 검사는 서버에서 수행한다. 화면에서 메뉴나 버튼을 숨기는 것만으로 처리하지 않는다. |
| BR-004 | 매장 · 사용자 · 상품 · 공급처는 삭제하지 않고 사용 안 함(비활성) 상태로 관리한다. 카테고리는 삭제 기능을 제공하지 않는다. |
| BR-005 | 판매 · 발주 · 재고 변동은 처리자와 처리 일시를 기록한다. |
| BR-006 | 날짜와 시간은 한국 시간(Asia/Seoul) 기준이다. |

### 6.2 매장 · 사용자

| ID | 규칙 |
|---|---|
| BR-010 | 매장코드는 중복될 수 없다. |
| BR-011 | MANAGER · USER는 반드시 1개 매장에 소속된다. ADMIN은 소속 매장이 없다. |
| BR-012 | 아이디는 중복될 수 없다. 비밀번호는 암호화(BCrypt)하여 저장한다. |
| BR-013 | 비활성 사용자는 로그인할 수 없다. |
| BR-014 | 사용 안 함 상태의 매장에서는 판매 · 발주를 새로 등록할 수 없다. |

### 6.3 상품 · 기준정보

| ID | 규칙 |
|---|---|
| BR-020 | 상품코드는 중복될 수 없다. |
| BR-021 | 카테고리 · 상품 · 공급처는 전 매장 공통 정보이며 ADMIN만 등록 · 수정할 수 있다. |
| BR-022 | 판매가는 전 매장 동일하다. |
| BR-023 | 사용 안 함 상태의 상품은 새로 판매 · 발주할 수 없다. 기존 판매 · 발주 · 재고 이력은 그대로 유지한다. |
| BR-024 | 카테고리는 1단계로 구성한다. (하위 카테고리 없음) |

### 6.4 재고

| ID | 규칙 |
|---|---|
| BR-030 | 재고는 **매장 × 상품** 단위로 관리한다. |
| BR-031 | 재고는 다음 4가지 업무로만 변경된다: **판매(−), 판매 취소(+), 발주 입고(+), 재고 조정(±)**. 재고 수량을 직접 수정하는 기능은 두지 않는다. |
| BR-032 | 모든 재고 변동은 재고 이력으로 남긴다. 이력에는 변동 유형, 변동 수량, 변동 전 · 후 수량, 관련 판매번호 · 발주번호, 사유(조정 시), 처리자, 처리 일시를 기록한다. |
| BR-033 | 재고 수량은 0보다 작아질 수 없다. |
| BR-034 | 재고 조정 시 사유 입력은 필수다. |
| BR-035 | 안전재고는 매장 × 상품별로 설정한다. 현재 수량이 안전재고보다 적으면 **부족 재고**로 판단한다. |
| BR-036 | 재고 변경과 재고 이력 기록은 원래 업무(판매 · 판매 취소 · 입고 · 조정)와 **하나의 트랜잭션**으로 처리한다. 하나라도 실패하면 전체를 취소(롤백)한다. |

### 6.5 판매

| ID | 규칙 |
|---|---|
| BR-040 | 판매 상품 중 하나라도 판매 수량이 현재 재고보다 많으면 판매 전체를 처리하지 않는다. |
| BR-041 | 판매 상세에는 판매 시점의 판매가를 저장한다. 이후 상품 판매가가 바뀌어도 과거 판매 금액은 변하지 않는다. |
| BR-042 | 판매 금액은 상품별 (단가 × 수량)의 합계다. 할인과 결제수단은 다루지 않는다. |
| BR-043 | 하나의 판매에 같은 상품을 중복해서 담을 수 없다. (수량으로 합산) 수량은 1 이상이다. |
| BR-044 | 판매 상태는 '완료', '취소' 두 가지다. |
| BR-045 | 완료된 판매는 수정할 수 없다. 변경이 필요하면 취소 후 다시 등록한다. |
| BR-046 | 판매 취소는 전체 취소만 가능하며 '완료' 상태에서만 할 수 있다. 취소 시 판매 수량만큼 재고를 복원한다. |
| BR-047 | 판매번호는 시스템이 자동으로 부여한다. (형식은 ⑦ 코드 정의서에서 확정) |

### 6.6 발주

| ID | 규칙 |
|---|---|
| BR-050 | 발주 상태는 **작성 → 승인 → 입고완료** 순서로 진행한다. '작성' · '승인' 상태에서만 **취소**할 수 있다. |
| BR-051 | 발주는 매장 단위로 처리하며, 발주한 매장으로 입고된다. |
| BR-052 | 발주 1건은 공급처 1곳에 대한 발주다. |
| BR-053 | 발주 단가의 기본값은 상품 매입가이며, 발주 등록 · 수정 시 변경할 수 있다. |
| BR-054 | '작성' 상태에서만 발주 내용을 수정할 수 있다. |
| BR-055 | 입고는 발주 수량 전량을 한 번에 처리한다. (부분 입고 없음) |
| BR-056 | '입고완료' · '취소' 상태의 발주는 더 이상 변경할 수 없다. |
| BR-057 | 발주를 등록한 사람이 직접 승인할 수 있다. |
| BR-058 | 발주번호는 시스템이 자동으로 부여한다. (형식은 ⑦ 코드 정의서에서 확정) |

### 6.7 매출 집계

| ID | 규칙 |
|---|---|
| BR-060 | 매출은 '완료' 상태의 판매만 집계한다. 취소된 판매는 제외한다. |
| BR-061 | 매출은 판매일 기준으로 집계한다. 이전 날짜의 판매가 오늘 취소되면 해당 판매일의 매출에서 빠진다. |

## 7. 비기능 요구사항

| ID | 구분 | 요구사항 |
|---|---|---|
| NFR-001 | 보안 | JWT 기반 인증을 사용하고, 인증 토큰은 요청 헤더(`Authorization: Bearer`)로 전달한다. |
| NFR-002 | 보안 | 비밀번호는 BCrypt로 암호화하여 저장하고, 응답에 포함하지 않는다. |
| NFR-003 | 데이터 정합성 | 재고 변경은 BR-036에 따라 트랜잭션 단위로 처리한다. |
| NFR-004 | 동시성 | 같은 매장 · 상품의 재고를 여러 요청이 동시에 변경해도 수량이 틀어지지 않아야 한다. (예: 남은 재고 1개를 두 판매가 동시에 요청하면 하나만 성공) |
| NFR-005 | 추적성 | 주요 데이터는 생성 · 수정 일시를 기록한다. |
| NFR-006 | API | REST 방식이며 모든 경로는 `/api/v1`로 시작한다. 응답 형식은 ⑥ API 명세에서 정의한다. |
| NFR-007 | 조회 | 목록 조회는 페이지 단위로 제공한다. (기본 20건) |
| NFR-008 | 환경 | Docker로 실행할 수 있어야 하며, DB 접속 정보 등 설정은 환경변수로 관리한다. |
| NFR-009 | 화면 | PC 화면(최신 Chrome · Edge)을 기준으로 한다. |

## 8. 용어 정의

| 용어 | 설명 |
|---|---|
| 본사 | 상품 · 카테고리 · 공급처 · 매장 · 사용자를 관리하는 조직. ADMIN이 해당한다. |
| 매장 | 판매 · 재고 · 발주가 이루어지는 영업 단위 |
| 기준정보 | 여러 업무에서 공통으로 사용하는 정보 (매장, 사용자, 카테고리, 상품, 공급처) |
| 재고 | 특정 매장이 보유한 특정 상품의 현재 수량 |
| 안전재고 | 매장 · 상품별로 유지해야 하는 최소 수량 |
| 부족 재고 | 현재 수량이 안전재고보다 적은 상태 |
| 재고 이력 | 재고가 변경될 때마다 남기는 변동 기록 |
| 재고 조정 | 실사 결과 등으로 재고 수량을 보정하는 작업 |
| 발주 | 매장이 공급처에 상품을 주문하는 업무 |
| 입고 | 발주한 상품을 받아 재고에 반영하는 업무 |
| 판매 취소 | 완료된 판매를 무효화하고 재고를 복원하는 업무 |
| 사용 중지 / 비활성 | 데이터를 삭제하지 않고 새 업무에 사용하지 못하게 하는 상태 |
