> **상태: 확정 (2026-10-01).** 2단계에서 `01-requirements.md`(3 · 4 · 5 · 6 · 9장)와 6장의 관련 문서로 옮긴 뒤 이 파일은 삭제한다.
> 코드 값(이력 유형 · 관련 문서 유형)과 테이블 · API 이름은 2단계 이후 ④ 테이블 정의 · ⑥ API 명세 · ⑦ 코드 정의서에서 확정한다. (명칭 고정 원칙)

## 1. 실무 장면

> 강남점에는 반팔 티셔츠가 30개 남아 있고, 홍대점은 2개뿐이라 주말 판매가 걱정이다.
> 강남점 점장(MANAGER)이 반팔 티셔츠 10개를 홍대점으로 보내기로 하고, 시스템에 **재고 이동**을 등록한다.
> 등록하는 순간 강남점 재고는 30 → 20, 홍대점 재고는 2 → 12가 되고, 두 매장의 재고 이력에 각각 기록이 남는다.
> 홍대점 점장은 재고 이동 목록에서 "강남점에서 받은 이동"을 확인하고, 재고 이력에서 언제 · 누가 보냈는지 확인한다.

- 등장인물: ADMIN(본사), MANAGER(보내는 매장 · 받는 매장 점장)
- 입력: 출발 매장, 도착 매장, 상품별 수량, 메모(선택)
- 결과: 이동 문서 1건, 출발 매장 재고 감소, 도착 매장 재고 증가, 재고 이력 (상품 수 × 2건)

## 2. 결정표

| # | 질문 | 결정 (제안) | 이유 |
|---|---|---|---|
| D1 | 이동 방식 | **즉시 이동** — 등록하는 순간 양쪽 재고가 바뀜 | 2단계(출고 → 이동 중 → 입고 확인)는 "이동 중 재고" 상태와 부분 도착 처리가 필요해 범위가 크게 늘어남. 1차는 즉시 이동, 2단계는 2차 검토 |
| D2 | 누가 등록하나 | ADMIN: 출발 · 도착 모두 선택<br/>MANAGER: **소속 매장이 출발**인 이동만 | 재고를 내보내는 쪽이 실물 출고 책임자. 다른 매장 재고를 마음대로 가져오는 것을 막음 |
| D3 | USER는 | 재고 이동 메뉴 사용 불가. 재고 이력에서 이동 기록은 보이지만 이동번호는 링크 없이 텍스트 | 발주와 같은 "매장 운영(점장 이상)" 업무. 재고 이력 화면의 발주번호 처리 방식(02-screens)과 동일 |
| D4 | 조회 범위 | ADMIN: 전체 (매장 조건 검색)<br/>MANAGER: 소속 매장이 **출발 또는 도착**인 이동 | 받는 쪽 점장도 들어온 재고를 확인해야 함 |
| D5 | 여러 상품을 한 번에 | 가능, 최대 50개 | 판매 · 발주 등록과 같은 상한 |
| D6 | 수량 | 1 이상 9,999 이하, 같은 상품 중복 불가 | 판매 수량 규칙(BR-043)과 동일 |
| D7 | 출발 = 도착 | 불가 | 재고 변화가 없는 무의미한 문서 |
| D8 | 사용 중지 매장 | 출발 · 도착 모두 **사용 중**이어야 함 | 판매 · 발주 등록과 동일 기준 (사용 중지 매장에서는 업무 불가) |
| D9 | 사용 중지 상품 | **사용 중인 상품만** 이동 | 판매 · 발주 등록과 동일 기준 (5장 Q1) |
| D10 | 재고 부족 | 상품 하나라도 부족하면 **이동 전체 거부** | 판매(BR-040)와 같은 원칙. 일부만 옮겨지면 문서와 실물이 어긋남 |
| D11 | 수정 · 취소 | **불가**. 잘못 이동했으면 반대 방향 이동을 새로 등록 | 즉시 이동이라 도착 매장이 이미 판매했을 수 있음 → 취소 시 도착 매장 재고 부족 가능. 반대 이동 문서로 남기는 편이 이력이 명확 |
| D12 | 상태값 | 두지 않음 (등록 = 완료) | 즉시 이동 + 취소 없음이면 상태가 하나뿐. 2단계 이동을 도입할 때 추가 |
| D13 | 금액 | 다루지 않음 | 같은 회사 매장 간 이동이라 매출 · 매입이 아님 |
| D14 | 메모 | 선택 입력, 200자 이하 | 이동 이유(예: "주말 행사 대비")를 남길 수 있게. 조정 사유와 달리 필수 아님 |
| D15 | 이동번호 | 시스템 자동 부여. `TR-{출발매장코드}-{yyyyMMdd}-{순번 6자리}` | 판매(`S-`) · 발주(`PO-`)와 같은 체계. 문서를 만드는 쪽(출발) 매장 코드 사용 |
| D16 | 재고 이력 | 상품마다 출발 매장에 **이동 출고(−)**, 도착 매장에 **이동 입고(+)** 1건씩. 관련 문서 = 재고 이동(이동번호) | 매장별 재고 이력만 봐도 들어오고 나간 경로를 알 수 있어야 함 |
| D17 | 매출 · Dashboard | 매출 집계에 영향 없음. 재고 수치(보유 상품 · 부족 재고)는 바뀐 재고 그대로 반영 | 이동은 판매가 아님 |

## 3. 예외 상황과 기대 결과

| 상황 | 기대 결과 |
|---|---|
| 출발 매장 재고 부족 (상품 하나라도) | 이동 전체 거부 (409 재고 부족). 아무 재고도 바뀌지 않음 |
| 출발 매장 = 도착 매장 | 거부 (400 입력 오류) |
| 같은 상품 중복, 수량 0 · 음수 · 9,999 초과, 상품 0개 · 51개 이상 | 거부 (400 입력 오류) |
| 사용 중지된 출발 · 도착 매장, 사용 중지 상품 | 거부 (400) |
| USER가 등록 · 조회 시도 | 403 |
| MANAGER가 다른 매장을 출발 매장으로 지정 | 출발 매장은 소속 매장으로 고정 (요청 값 무시). 다른 매장 간 이동 상세 조회는 403 |
| 같은 출발 재고에 판매와 이동이 동시에 | 재고가 음수가 되지 않음. 늦게 처리된 쪽은 최신 재고 기준으로 판단해 부족하면 거부 |
| 강남 → 홍대, 홍대 → 강남 이동이 동시에 | **둘 다 정상 처리** (교착 상태 오류 없음). 처리 후 매장별 재고 = 시작 재고 ± 이동 수량 |

### 4.3 업무 규칙 (6.8 재고 이동)

| ID | 규칙 |
|---|---|
| BR-070 | 재고 이동은 한 매장(출발)의 재고를 다른 매장(도착)으로 옮기는 업무다. **등록 즉시 완료**되며, 이동 문서 저장 · 출발 매장 재고 차감 · 도착 매장 재고 증가 · 재고 이력 기록을 **하나의 트랜잭션**으로 처리한다. |
| BR-071 | 출발 매장과 도착 매장은 서로 달라야 하며, 두 매장 모두 사용 중이어야 한다. |
| BR-072 | MANAGER는 소속 매장을 출발 매장으로 하는 이동만 등록할 수 있다. ADMIN은 출발 · 도착 매장을 모두 선택한다. USER는 재고 이동 업무를 사용할 수 없다. |
| BR-073 | 이동 상품 중 하나라도 이동 수량이 출발 매장의 현재 재고보다 많으면 이동 전체를 처리하지 않는다. |
| BR-074 | 하나의 이동에 같은 상품을 중복해서 담을 수 없다. 상품은 최대 50개, 수량은 1 이상 9,999 이하다. 사용 중인 상품만 이동할 수 있다. |
| BR-075 | 재고 이동은 수정하거나 취소할 수 없다. 잘못 이동한 경우 반대 방향의 이동을 새로 등록한다. |
| BR-076 | 재고 이동 시 상품마다 출발 매장에 '이동 출고(−)', 도착 매장에 '이동 입고(+)' 재고 이력을 남기고, 관련 문서로 이동번호를 기록한다. |
| BR-077 | 재고 이동은 금액과 매출 집계에 영향을 주지 않는다. 이동 전후 전체 매장의 상품별 재고 합계는 같다. |
| BR-078 | MANAGER는 소속 매장이 출발 또는 도착인 이동만 조회할 수 있다. |
| BR-079 | 이동번호는 시스템이 자동으로 부여한다. (형식은 ⑦ 코드 정의서에서 확정) |
