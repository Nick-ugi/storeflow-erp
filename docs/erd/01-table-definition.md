## 1. 설계 원칙

| 항목 | 규칙 |
|---|---|
| PK | 모든 테이블 `id BIGINT GENERATED BY DEFAULT AS IDENTITY` |
| 금액 | `BIGINT`, 원 단위 정수 (BR-001). 합계 금액이 INTEGER 범위를 넘을 수 있어 BIGINT 사용 |
| 수량 | `INTEGER` |
| 일시 | `TIMESTAMPTZ`. 저장은 절대 시각, 표시 · 날짜 집계는 Asia/Seoul 기준 (BR-006) |
| 문자열 | `VARCHAR(n)`. PostgreSQL의 n은 **바이트가 아닌 문자 수**이므로 한글도 n자까지 저장된다. |
| 상태 · 유형 | `VARCHAR(20)` + CHECK 제약. 값은 [코드 정의서](03-code-definition.md) 참고 |
| 삭제 | 업무 데이터는 물리 삭제하지 않는다. 예외: '작성' 상태 발주를 수정할 때 발주 상세를 지우고 다시 저장 |
| 감사 컬럼 | `created_at`, `updated_at` (변경 시 애플리케이션이 `updated_at = now()` 설정), 처리자는 `*_by` |
| 업무 규칙 보장 | 재고 음수 금지, 이력 계산식, 상태 흐름 등 핵심 규칙은 **애플리케이션과 DB 제약조건 양쪽에서** 막는다. (5장) |

### 1.1 원래 계획 대비 변경 사항

| 항목 | 원래 계획 | 변경 | 이유 |
|---|---|---|---|
| 매장 | 없음 | `stores` 추가, `users` · `stocks` · `stock_histories` · `sales` · `purchase_orders`에 `store_id` 추가 | 다중 매장 (요구사항 1.2) |
| 안전재고 | `products.safety_stock` | `stocks.safety_stock` | 매장별 안전재고 (BR-035) |
| 재고 행 | 상품당 1행 | 매장 × 상품당 1행 (`uk_stocks_store_id_product_id`) | BR-030 |
| 처리자 · 취소 정보 | `created_by`만 | 승인 · 입고 · 취소 일시와 처리자, 수정자 추가 | BR-005, 상세 기능 명세 |
| 재고 이력 | - | `reason`(조정 사유), `created_by`(처리자) 추가 | BR-032, BR-034 |

## 2. 명명 규칙

| 대상 | 규칙 | 예 |
|---|---|---|
| 테이블 | 소문자 snake_case, 복수형 | `purchase_orders` |
| 컬럼 | 소문자 snake_case | `sale_price` |
| FK 컬럼 | `{참조 테이블 단수형}_id` | `store_id`, `purchase_order_id` |
| 일시 · 처리자 | `{동작}_at`, `{동작}_by` | `approved_at`, `approved_by` |
| 코드 · 이름 | `{대상}_code`, `{대상}_name` | `product_code`, `store_name` |
| 제약조건 | `pk_{테이블}`, `uk_{테이블}_{컬럼}`, `fk_{테이블}_{컬럼}`, `ck_{테이블}_{설명}` | `uk_stocks_store_id_product_id` |
| 인덱스 | `idx_{테이블}_{컬럼}` | `idx_sales_store_id_sold_at` |
| 시퀀스 | `{용도}_seq` | `sale_number_seq` |

- Java에서는 MyBatis `map-underscore-to-camel-case` 설정으로 `sale_price` ↔ `salePrice`로 자동 매핑된다.

### 4.8 `stock_histories` — 재고 이력

| 컬럼 | 논리명 | 타입 | NULL | 기본값 | 키 | 설명 |
|---|---|---|---|---|---|---|
| id | 재고 이력 ID | BIGINT | N | IDENTITY | PK | |

| product_id | 상품 ID | BIGINT | N | | FK | → `products.id` |

| reference_type | 관련 문서 유형 | VARCHAR(20) | Y | | | `SALE` / `PURCHASE_ORDER`. 조정은 NULL |

  - `ck_stock_histories_quantity`: 변동 수량 ≠ 0, 변동 전 · 후 수량 ≥ 0, **변동 후 = 변동 전 + 변동 수량**
  - `ck_stock_histories_type`: 유형별 부호와 관련 문서 조합 (판매는 감소 + 판매 문서, 판매 취소 · 입고는 증가 + 해당 문서, 조정은 관련 문서 없음 + 사유 필수)
- 인덱스: `idx_stock_histories_store_id_product_id_created_at`, `idx_stock_histories_created_at`, `idx_stock_histories_reference`
- `reference_id`는 유형에 따라 다른 테이블을 가리키므로 FK를 걸 수 없다. `ck_stock_histories_type`으로 유형과 문서 종류의 조합을 보장하고, 대상 존재 여부는 재고 변경 공통 절차가 같은 트랜잭션에서 보장한다.

- 인덱스: `idx_purchase_orders_store_id_ordered_at`, `idx_purchase_orders_ordered_at`, `idx_purchase_orders_supplier_id`

## 5. DB 제약조건으로 함께 보장하는 업무 규칙

애플리케이션 검증이 빠지거나 잘못되어도 **DB가 마지막으로 막는** 규칙이다.

| 업무 규칙 | 제약조건 |
|---|---|
| BR-033 재고는 0보다 작아질 수 없다 (BR-040 재고 부족 판매 차단의 최종 방어선) | `ck_stocks_quantity` |
| BR-030 재고는 매장 × 상품 단위 | `uk_stocks_store_id_product_id` |
| BR-032 이력의 변동 전 · 후 수량 계산 | `ck_stock_histories_quantity` |
| BR-031 · BR-034 변동 유형별 부호, 관련 문서, 조정 사유 필수 | `ck_stock_histories_type` |
| BR-043 한 판매에 같은 상품 중복 불가 | `uk_sale_items_sale_id_product_id` |
| BR-042 금액 = 단가 × 수량 | `ck_sale_items_price`, `ck_purchase_order_items_price` |
| BR-044 · BR-046 판매 상태와 취소 정보 일치 | `ck_sales_status` |
| BR-050 · BR-056 발주 상태 흐름과 단계별 처리 정보 | `ck_purchase_orders_status`, `ck_purchase_orders_processor` |
| BR-010 · BR-012 · BR-020 코드 · 아이디 중복 불가 | `uk_stores_store_code`, `uk_users_username`, `uk_products_product_code` |

**애플리케이션에서만 보장하는 규칙**
- BR-011 역할별 매장 소속 (ADMIN은 매장 없음, MANAGER · USER는 필수) — 역할이 다른 테이블(`roles`)에 있어 CHECK로 검사할 수 없음
- `stocks.quantity`와 해당 매장 · 상품의 마지막 `stock_histories.after_quantity` 일치 — 재고 변경 공통 절차가 같은 트랜잭션에서 보장

## 6. 인덱스 설계 근거

| 인덱스 | 사용처 |
|---|---|
| `idx_sales_store_id_sold_at` | 판매 내역(매장 + 기간), Dashboard 매출 집계 (소속 · 선택 매장) |
| `idx_sales_sold_at` | ADMIN 전체 매장 판매 내역 · 매출 |
| `idx_purchase_orders_store_id_ordered_at` | 발주 목록(매장 + 기간), Dashboard 최근 발주 |
| `idx_purchase_orders_ordered_at` | ADMIN 전체 매장 발주 목록 |
| `idx_purchase_orders_supplier_id` | 발주 목록의 공급처 조건 |
| `idx_stock_histories_store_id_product_id_created_at` | 재고 상세의 최근 변동 10건, 재고 이력(매장 + 상품) |
| `idx_stock_histories_created_at` | 재고 이력 기간 조회 (ADMIN 전체) |
| `idx_stock_histories_reference` | 판매 · 발주 1건의 재고 변동 조회 |
| `idx_stocks_product_id` | 상품 목록의 전 매장 재고 합계 |
| `idx_users_role_id`, `idx_users_store_id` | 사용자 목록 조건 |
| `idx_products_category_id` | 상품 목록 · 현재 재고의 카테고리 조건 |
| `idx_sale_items_product_id`, `idx_purchase_order_items_product_id` | 상품 참조 확인 (FK) |

- PostgreSQL은 FK 컬럼에 인덱스를 자동으로 만들지 않으므로 조회에 쓰는 FK에 직접 만든다.
- 처리자 FK(`created_by` 등)는 조회 조건으로 쓰지 않으므로 인덱스를 만들지 않는다.
- 상품명 부분 일치 검색(`LIKE '%키워드%'`)은 일반 인덱스를 쓰지 못한다. 데이터 규모가 작아 인덱스 없이 시작한다.
