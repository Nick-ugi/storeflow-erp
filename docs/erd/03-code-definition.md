## 1. 코드 관리 방식

- 코드 값은 영문 대문자 + 밑줄(`SALE_CANCEL`)로 쓴다.
- DB에는 코드 값을 `VARCHAR(20)`으로 저장하고 **CHECK 제약**으로 허용 값을 제한한다.
- Java에서는 코드 그룹마다 **enum**으로 정의해 오타가 컴파일 단계에서 걸리도록 한다. (구현 단계)
- 화면에 보여줄 한글 이름은 프론트엔드가 코드 값 → 한글 이름으로 변환한다.
- 별도의 공통코드 테이블은 두지 않는다. 코드가 적고 거의 바뀌지 않으며, 코드 값에 따라 업무 로직이 달라지므로 enum으로 관리하는 편이 안전하다.

## 2. 코드 목록

### 2.1 역할 — `roles.role_name`

| 코드 | 이름 | 설명 |
|---|---|---|
| `ADMIN` | 본사 관리자 | 전 매장 데이터, 기준정보 · 매장 · 사용자 관리 |
| `MANAGER` | 매장 관리자 | 소속 매장의 판매 · 재고 · 발주 |
| `USER` | 매장 직원 | 소속 매장의 판매 등록, 재고 조회 |

### 2.2 사용 상태 — `stores.status`, `products.status`, `suppliers.status`, `users.status`

| 코드 | 이름 (매장 · 상품 · 공급처) | 이름 (사용자) |
|---|---|---|
| `ACTIVE` | 사용 | 활성 |
| `INACTIVE` | 사용 중지 | 비활성 |

### 2.3 판매 상태 — `sales.status`

| 코드 | 이름 | 필수 항목 |
|---|---|---|
| `COMPLETED` | 완료 | 판매 일시, 처리자 |
| `CANCELLED` | 취소 | 위 항목 + 취소 일시, 취소 처리자 |

### 2.4 발주 상태 — `purchase_orders.status`

| 코드 | 이름 | 필수 항목 | 다음 상태 |
|---|---|---|---|
| `DRAFT` | 작성 | 발주 일시, 작성자 | `APPROVED`, `CANCELLED` |
| `APPROVED` | 승인 | 위 항목 + 승인 일시, 승인자 | `COMPLETED`, `CANCELLED` |
| `COMPLETED` | 입고완료 | 위 항목 + 입고 일시, 입고 처리자 | 없음 |
| `CANCELLED` | 취소 | 발주 일시, 작성자, 취소 일시, 취소 처리자 | 없음 |

### 2.5 재고 변동 유형 — `stock_histories.type`

| 코드 | 이름 | 변동 방향 | 관련 문서 유형 | 사유 |
|---|---|---|---|---|
| `SALE` | 판매 | − | `SALE` | - |
| `SALE_CANCEL` | 판매 취소 | + | `SALE` | - |
| `PURCHASE` | 입고 | + | `PURCHASE_ORDER` | - |
| `ADJUSTMENT` | 조정 | + 또는 − | 없음 | 필수 |

### 2.6 관련 문서 유형 — `stock_histories.reference_type`

| 코드 | 이름 | `reference_id`가 가리키는 대상 |
|---|---|---|
| `SALE` | 판매 | `sales.id` |
| `PURCHASE_ORDER` | 발주 | `purchase_orders.id` |

## 3. 번호 체계

| 구분 | 형식 | 예 |
|---|---|---|
| 판매번호 (`sales.sale_number`) | `S-{매장코드}-{YYYYMMDD}-{순번}` | `S-GN01-20260925-000001` |
| 발주번호 (`purchase_orders.order_number`) | `PO-{매장코드}-{YYYYMMDD}-{순번}` | `PO-GN01-20260925-000001` |

- **날짜**: 등록 시점의 한국 날짜(Asia/Seoul)
- **순번**: DB 시퀀스(`sale_number_seq`, `purchase_order_number_seq`) 값을 6자리로 0을 채워 붙인다. 6자리를 넘으면 자리수가 늘어난다.
- 순번은 **전 매장 공통이며 날짜별로 다시 시작하지 않는다.** 따라서 번호는 항상 중복되지 않고, 채번할 때 다른 판매를 기다리게 하는 잠금이 없다.
- 트랜잭션이 롤백되면(예: 재고 부족) 가져온 순번은 사용되지 않고 건너뛴다. **번호가 빠짐없이 이어지는 것은 보장하지 않는다.**
- 최대 길이: 매장코드 10자, 순번 8자리까지 가정해도 40자 이내 (`VARCHAR(40)`)

## 4. 원래 계획 대비 변경 사항

| 항목 | 원래 계획 | 확정 코드 | 이유 |
|---|---|---|---|
| 직원 역할 | `STAFF` | `USER` | 역할 이름 결정 (요구사항 2장) |
| 판매 취소 재고 이력 유형 | `RETURN` (반품) | `SALE_CANCEL` | 반품이 아니라 판매 전체 취소만 다룸 (BR-046). 반품은 범위 제외 |
| 발주 완료 상태 | `COMPLETED` | `COMPLETED` (유지) | 입고완료를 뜻함 |

## 5. 확정 시 결정 사항

| # | 항목 | 결정 | 채택하지 않은 안 |
|---|---|---|---|
| 1 | 코드 관리 방식 (1장) | CHECK 제약 + Java enum | 공통코드 테이블 (코드 그룹 · 코드 · 이름을 DB에서 관리) |
| 2 | 번호 순번 (3장) | 전 매장 공통 시퀀스, 날짜별 초기화 없음, 번호 건너뜀 허용 | 매장 · 날짜별로 0001부터 시작 (채번 테이블 + 잠금 필요, 같은 매장 판매가 채번에서 대기) |
| 3 | 판매 취소 유형 코드 | `SALE_CANCEL` | 원래 계획의 `RETURN` |
